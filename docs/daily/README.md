## 每天操作完，代码应该长什么样

63 个学习日都增加了 **“当天写完后的参考代码”**，直接放在当天操作步骤之后、完成判定之前。每份参考都给出目标文件路径、完整代码或完整的本日追加内容、关键解释、运行命令和应看到的结果。

- **新建/完整版本**：对照该天结束时文件应有的内容；已有个人代码先比较再合并，不直接覆盖自己的成果。
- **追加**：把本段接在前几天的同一文件后，沿用前面的 import、fixture 和函数；已写过同名函数则更新它，只保留一份。
- **替换函数**：只替换点名的函数和装饰器，其余 fixture、import、个人代码保留。
- **删除实验文件**：只删除点名的临时故意失败文件，避免污染后续正常回归。

设计日提供完整用例表、状态表或交付说明；SQL 日提供查询；Linux/CI/JMeter 日提供实际脚本、YAML、完整 JMX 或指标处理代码。代码里的日期、CI 链接、实际性能数据仍需本人执行后填写，参考答案不会虚构这些结果。

例如，第 1 天给出三条完整加法测试，第 2 天给出 `reverse_string` 实现及完整测试，第 6 天给出四个字符串函数与全部边界测试。第九阶段同时给出归档测试和分步完成的服务实现，便于逐处对照。

所有参考还单独存放在 [每日参考文件目录](reference/README.md)。该目录是答案存档，不自动改变项目的 `src/` 或 `tests/`。先按当天的目标路径练习，再用参考逐行核对；不要把整个答案目录复制进 tests。

PowerShell 脚本中的中文在 Windows PowerShell 5 下需要 UTF-8 **带 BOM** 保存；单独提供的 `.ps1` 参考文件已经采用该编码。Bash 脚本用 UTF-8、LF 换行。复制教程代码块到编辑器时也按对应格式保存。

## 开始前准备一次

先确认会 Python 的变量、函数调用、缩进、列表/字典、import 和基本类实例化。若第一天的逐行解释仍看不懂，先补这些语法；不需要提前学装饰器或 pytest 插件。

打开 PowerShell，进入项目根目录。以下是你当前机器的路径；换机器后改成实际路径：

```powershell
Set-Location D:\pythonProject\auto-test-study
Test-Path .venv\Scripts\python.exe
```

若显示 `False`，再执行以下命令；已有可用环境就不要重复创建：

```powershell
py -3.11 -m venv .venv
```

安装项目依赖并确认 pytest 可用：

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pytest --version
```

预期最后一条输出 pytest 版本。若 `py` 不存在，先安装 Python 3.11 并重开终端；安装依赖失败先处理网络/安装错误，不要跳到写测试。

本手册前五阶段、阶段七与九的命令默认是 **Windows PowerShell、项目根目录**。阶段六使用 **Linux Bash**，阶段八会单独标注。文中的代码块要粘到指定文件；终端命令才在终端执行。

## 每天固定怎么操作

1. 用 5 分钟看当天目标，只打开“材料”列出的文件。
2. 用 10—20 分钟阅读指定函数或测试，写下你认为应该出现的结果。
3. 用 30—60 分钟完成当天动手任务；有卡点就对照当天完整参考代码，再运行给出的命令。
4. 用 10—20 分钟做验收：改变输入、观察失败、恢复并重跑。
5. 用 5 分钟留下学习记录；没通过就记“待完成”和具体卡点。

可以复制下列模板到 `docs/learning_log.md`，每一天加一段。这个文件由你填写，教程不会替你预填“通过”。报告大文件放 `reports/learning/`；该目录被 Git 忽略，需要长期留证时另行保存，或在学习记录中保留精简、脱敏的关键输出。

```markdown
## 1-1 / 实际学习日期：
- 目标：
- 我新增或修改的文件、测试名：
- 执行命令：
- 预期结果（运行前写）：
- 实际结果 / 退出码 / 证据路径：
- 我能解释的原因：
- 故意失败的改动、失败节点与恢复结果（当天要求时填写）：
- 验收勾选：
- 结论：已完成 / 待完成；下一步：
```

## 如何判定自己完成了

**“看懂了”“复制后全绿”“看了两个小时”都不足以单独证明完成。** 每天至少留下一个自己动手的产物，逐项满足当天的“完成判定”，并用自己的话回答自测问题。周末再按“不看样例重做”的要求验收。

- 样例通过：说明环境和现有样例能工作。记录为“基线通过”。
- 自写任务通过：说明你完成了这次练习，还需核对测试是否断言了正确的规则。
- 要求故障实验的日子：保留“正确时通过 → 注入缺陷时失败 → 恢复后通过”三段证据。失败必须发生在目标断言，语法或导入错误不算捕获业务缺陷。
- 没有 Linux、GitHub 或 JMeter 环境：记录“环境待准备”，继续能做的阅读/设计；对应实操验收保持未完成，不能用 Windows 或模拟输出替代。

## 卡住时按这个顺序查

| 现象 | 先做什么 |
|---|---|
| 找不到 Python / pytest | 回到环境准备，使用 `.venv` 的完整解释器路径 |
| 找不到文件 / `ModuleNotFoundError` | 确认终端在项目根目录，文件名与 import 路径一致 |
| `no tests ran` | 文件以 `test_` 开头、函数以 `test_` 开头；运行 `--collect-only` |
| `fixture not found` | 检查拼写；业务测试要放 `tests/workflow/` 才能使用该目录的 fixture |
| `FAILED` | 先看失败测试名、行号、预期/实际，再核对需求；参考 [排障指南](../DEBUGGING.md) |
| 故意改坏功能，测试仍通过 | 检查是否运行了目标测试、是否只断言状态码、是否漏测该边界 |

需要求助时提供：学习日编号、运行命令、完整相关报错、你预期发生什么、已经尝试了什么。先保存证据，再修改代码。

故障实验每次只改一处并手动恢复该处。不要用整文件覆盖、`git reset --hard` 或删除数据库的方式恢复，以免丢掉自己的练习。每阶段结束可在核对差异后只提交自己的成果。

## 参考代码本身怎么验证

维护者或希望核对答案的学习者可以在项目根目录运行：

```powershell
.\.venv\Scripts\python.exe -m tools.check_daily_reference --static-only
.\.venv\Scripts\python.exe -m tools.check_daily_reference --stage 1
```

第一条检查 63 天覆盖、参考文件语法、XML/YAML 等；第二条在 `reports/learning/` 下的临时项目副本逐天应用第一阶段代码并运行测试，不覆盖你正在写的练习。去掉 `--stage 1` 可验证全部已配置的本机 Python/HTTP/SQL 实验，包括预期失败与恢复；设计日不伪装成测试已执行。

这类维护检查不会安装 Linux、下载 JMeter、推送 GitHub，也不会代替真实 Linux/CI/JMeter 的个人验收。
