# 从需求推导用例

先读 `API_CONTRACT.md`，再看代码。下面是设计样例，不代表已经覆盖所有风险。优先级表示风险判断，不等于执行顺序。

| 编号 | 需求 / 风险 | 前置与输入 | 预期结果 | 优先级 |
|---|---|---|---|---|
| TASK-01 | 正常业务闭环 | Alice 登录，创建 title=first | 201；用返回 ID 查到；更新后再查一致；删除 204 后查 404 | P0 |
| TASK-02 | 未认证写入 | 不携带 token 创建 | 401，未创建数据 | P0 |
| TASK-03 | 无效凭据 | 错误密码 / 伪造 token | 401 | P0 |
| TASK-04 | 水平越权 | Alice 建任务，Bob 按 ID GET/PUT/DELETE | 全部 403；Alice 再查数据未变 | P0 |
| TASK-05 | 列表隔离 | 两个用户分别创建唯一标题 | 各自列表只含自己的数据，检查每个元素 | P0 |
| TASK-06 | 空值等价类 | title 为缺失、空串、空白、null、数字、数组 | 400，列表中没有新增记录 | P1 |
| TASK-07 | 长度边界 | title 长度 1 / 80 / 81 | 1、80 成功；81 失败 | P1 |
| TASK-08 | 规范化 | title 首尾有空白 | 去除空白后存储，查询保持一致 | P1 |
| TASK-09 | 状态枚举 | status=open/done/unknown/null | 前两种成功，后两种 400 | P1 |
| TASK-10 | 更新原子性 | 合法 title + 非法 status | 400，title 和 status 都没有改变 | P1 |
| TASK-11 | 不存在资源 | 找到未分配 ID，GET/PUT/DELETE | 404 | P1 |
| TASK-12 | 非法 JSON | POST 发送截断 JSON | 400，服务仍可响应 health | P1 |
| TASK-13 | 字段保护 | 创建或更新时传 owner/id/未知字段 | 400，不改归属或 ID | P0 |
| TASK-14 | 重复删除 | 删除后再 DELETE 同一 ID | 首次 204，随后 404；按接口约定断言 | P1 |
| TASK-15 | 重启持久化 | 手动服务创建任务，重启并重新登录 | 原任务仍能查询，旧 token 失效 | P1 |

TASK-15 是保留给学习者的手动/自动扩展任务；样例测试不是此表的全部实现。完善用例时用编号标识，例如 `test_invalid_update_is_atomic` 对应 TASK-10，避免只有用例数量没有需求追溯。

## 断言顺序

1. 请求层：是否发生连接失败或超时？这些失败不能冒充业务通过。
2. HTTP 层：状态码是否符合当前场景，包括期望的 4xx？204 不解析 JSON。
3. 结构层：Schema 检查必需字段、类型、枚举、列表中所有元素。
4. 业务层：提交值、owner、状态变化是否符合要求？
5. 副作用：失败后是否没有新增/修改，成功后是否真正持久化？

优先级高的风险先自动化。合法与非法边界要成对选择，不要用几百条相似数据代替权限和业务状态测试。测试数据可以写在参数列表或 YAML 中；只有业务人员需要维护或数据集较大时，才值得抽离文件。

## 独立性与清理

每个用例自己准备账号上下文和资源，不能通过测试执行顺序传递 ID。工厂创建成功立即登记 ID，再执行断言，yield 后统一删除。测试已经删除过的资源允许清理时 404；网络失败或其他状态必须暴露，不能 blanket `except: pass`。服务和数据库以 worker 为边界隔离，客户端按函数隔离。

不要在共享环境使用“删除全部任务”来清理。迁移到公司环境时，用唯一业务前缀/专用租户、明确的资源登记表和回收策略，并先确认可操作范围。
