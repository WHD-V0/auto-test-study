# 把实际完成的内容写进简历，并经得起追问

教程最后一章。先按 [学习成果](LEARNING_OUTCOMES.md) 验收。下面是可改写的模板，不代表你已经完成；所有方括号、数量、时间和结果都必须替换成自己的证据，未完成的条目删除。

## 1. 先区分阅读、练习和项目能力

| 当前程度 | 合适表述 | 还需补什么 |
|---|---|---|
| 只看过章节或运行原有样例 | 学习中；简历通常无需单列为熟练技能 | 脱离范例新增场景并解释 |
| 自己完成过练习并能重做 | 了解/掌握基础，可描述实际任务 | 补独立交付、失败定位和证据 |
| 能独立实现并处理变更与失败 | 熟悉相关工具用于具体问题 | 用项目和结果支持，不只写形容词 |
| 实际公司/实习中负责并交付 | 如实描述真实职责和系统范围 | 区分团队成果与个人贡献 |

这是个人实战项目，应放在“个人项目/项目实践”，不能冒充企业工作经历。运行仓库已有的测试，不等于自己设计并编写了这些测试。

## 2. 技能栏示例（完成相应验收后使用）

- Python / pytest：能使用 fixture、参数化、Mock 和异常断言编写接口测试，并实现测试数据准备与清理。
- HTTP / 接口测试：能覆盖登录鉴权、权限隔离、CRUD、边界和异常，结合 Schema 与业务字段验证响应。
- SQL：能编写条件查询、JOIN、GROUP BY/HAVING 和 NULL 查询，理解事务，使用参数绑定核对接口落库数据；本项目实践数据库为 SQLite。
- Linux / Bash：能部署并运行测试环境，使用 ps、ss、curl 和日志定位常见问题，编写保留失败退出码的回归脚本。
- JMeter：能编写参数化与 token/ID 关联的脚本，使用断言、非 GUI 模式、JTL 与 HTML 报告完成基础负载实验。
- CI：能配置 GitHub Actions 自动回归并归档 JUnit/HTML 报告，理解失败退出码与环境隔离。

SQL 学的是通用基础，但 SQLite 实践不能写成“熟练 MySQL”；把查询迁移到 MySQL 并做过验证后，再据实补充数据库名称。JMeter 只有跑通短实验时，可写“掌握基础使用”，不直接写性能调优经验。

## 4. 数字应该从哪里来

| 想写的数字 | 可用证据 | 不应这样写 |
|---|---|---|
| 场景/用例数量 | 需求用例表、pytest collection，区分参数展开与业务场景 | 把原有样例数量全算成个人产出 |
| 缺陷数量 | 有编号、复现、修复验证的记录，标明是否注入 | 把环境失败、重复报错都算独立缺陷 |
| 回归耗时改善 | 同机器、同用例、相同条件，至少多轮记录 | 只比较两次偶然运行就写提升百分比 |
| 吞吐量/P95 | JTL、负载参数、样本数、环境、统计口径 | 把本机玩具服务结果写成生产承载能力 |
| CI 能力 | 自己仓库实际执行的成功与失败 run | 只有 YAML 文件就写已落地 CI |

证据目录建议：用例表、个人贡献说明、版本记录、报告、JTL、排障记录。不要上传凭据和真实公司数据。教程中的测试通过数是仓库当前结果，不是你可以直接复制的个人业绩。

## 5. 两分钟项目介绍示例

“我做的是一个个人接口测试实战项目，目标是验证任务创建、更新、删除和用户隔离。我基于教程样例新增了 [真实范围]，先按契约设计场景，再用 pytest 实现。数据通过 fixture 创建并登记，失败后也清理，每个 worker 独立服务和数据库。一次 [具体故障] 中，我先通过 [HTTP/日志/SQL 证据] 缩小范围，再定位到 [原因]，修复后补充了 [回归]。另外在 Linux 上跑通回归，并用 JMeter 完成了 [实际实验]。它是本地教学系统，结论适用于这一环境，我还没有做过 [实际未覆盖项]。”

换成自己的事实，不要背空白模板。面试官通常会从“个人新增”和“那次故障”继续追问。

## 6. 高频追问与回答要点

| 问题 | 回答应包含的具体内容 | 演示材料 |
|---|---|---|
| 为什么不是只断言 200？ | 结构、业务字段、权限、副作用、更新后再查 | test_tasks.py |
| 测试失败后怎么清数据？ | 先登记 ID，yield 清理，已删除允许 404，其他失败暴露 | workflow/conftest.py |
| 并行为什么不会互相污染？ | worker 独立端口/数据库；客户端与 token 按函数隔离 | fixture 和 -n 2 结果 |
| Mock 全绿能证明接口正确吗？ | 只能证明客户端对模拟响应的处理；服务逻辑需真实集成 | responses 与 workflow 对照 |
| POST 为什么不能随便重试？ | 超时不代表未写入；重复提交风险；幂等键需服务端约定 | 客户端重试测试 |
| LEFT JOIN 后 COUNT(*) 为什么多了？ | 无匹配仍保留行；COUNT(右表非空键) 才数真实匹配；一对多也会放大 | SQL 练习数据 |
| 事务如何体现到测试？ | 非法更新返回 400 且原字段都不变；数据库核对无部分写入 | 落库断言 |
| 接口慢，Linux 上先看什么？ | 先确认版本/负载/时间窗口，再看进程、端口、错误、CPU/内存/磁盘并做对照 | 排障记录 |
| pytest 失败但脚本成功为何？ | pipeline 默认可能返回 tee 状态；pipefail 保留上游失败 | run_regression.sh |
| JMeter 线程数等于 QPS 吗？ | 不等于；并发、响应时间、思考时间和请求比例共同影响吞吐 | 实验参数和 JTL |
| P95 和错误率怎么看？ | 按接口标签与窗口；P95 是响应时间百分位；断言失败也算错误 | JTL/HTML 报告 |
| JMeter 退出 0 就全绿吗？ | 不一定，要校验 success、错误数和预期样本数 | check_jtl.py |
| 你能证明性能瓶颈在哪吗？ | 给事实和对照实验，不能只因 SQLite 或 CPU 高就断言根因 | 性能报告的限制与下一步 |
| 你的个人贡献是什么？ | 清楚列出复用、修改、新增，展示对应差异及原因 | 贡献说明、提交或 diff |

## 7. 面试前的现场自测

不用 AI 代答，独立完成：写一个 LEFT JOIN；为新边界写参数化测试；解释一个失败栈；查一次端口；指出 Bash 退出码风险；修改 JMeter 线程/关联/断言并解释样本数。每题能结合自己的文件和结果讲清楚，比列十个“熟练掌握”更有说服力。
